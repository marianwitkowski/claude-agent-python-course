# Lekcja 8.3 — TDD: pisz test pierwszy

## Cel
Po lekcji uczeń:
- Rozumie cykl **Red → Green → Refactor**
- Pisze test PRZED napisaniem funkcji
- Iteracyjnie rozbudowuje funkcję, dodając testy
- Wie, kiedy TDD ma sens (a kiedy nie)

## Krok 1 — Zakotwiczenie (3 min)
**Pytanie wejściowe:**
> "Idziesz do egzaminu. Czy lepiej wiedzieć **z góry**, jakie pytania będą zadane?"

**Co chcesz usłyszeć:** tak — wiesz na czym się skupić, nie marnujesz czasu na rzeczy nieistotne. Test pełni rolę "egzaminu" — gdy znasz go z góry, piszesz kod celowo, nie "na wszelki wypadek".

## Krok 2 — Mostek (5 min)
**Mostek:** "TDD (Test-Driven Development) to praktyka, w której **najpierw piszesz test** (jak ma działać funkcja), **potem implementujesz** (żeby test przeszedł). Cykl:
1. **Red** — napisz test, który się **nie udaje** (bo funkcji jeszcze nie ma)
2. **Green** — napisz **najprostszy możliwy kod**, żeby test przeszedł
3. **Refactor** — popraw kod, ale testy nadal mają przechodzić"

**Pytanie:** "Co byś zyskał pisząc test pierwszy?"
- jasność celu (wiem dokładnie czego chcę)
- mniej "kodu na wszelki wypadek"
- gwarancja że testy są — bo gdy piszesz "potem", często nigdy

## Krok 3 — Eksperyment (15-20 min)

**Scenariusz: zaimplementuj funkcję `fizz_buzz(n)` metodą TDD.**

Reguły:
- Liczby od 1 do n
- Wielokrotności 3: "Fizz"
- Wielokrotności 5: "Buzz"
- Wielokrotności 3 i 5: "FizzBuzz"
- Inne: liczba jako string

### Red — pierwszy test:
```python
# test_fizzbuzz.py
from fizzbuzz import fizz_buzz

def test_zwraca_liste():
    assert isinstance(fizz_buzz(0), list)
```

`pytest` → **FAIL** (`ModuleNotFoundError: fizzbuzz`).

### Green — minimalny kod:
```python
# fizzbuzz.py
def fizz_buzz(n):
    return []
```

`pytest` → **PASS**. ✅

### Red — następny test:
```python
def test_jedynka_zwraca_jeden():
    assert fizz_buzz(1) == ["1"]
```

`pytest` → **FAIL** (zwraca `[]`).

### Green:
```python
def fizz_buzz(n):
    return [str(i) for i in range(1, n + 1)]
```

`pytest` → **PASS**. ✅

### Red — Fizz:
```python
def test_trojka_to_fizz():
    assert fizz_buzz(3) == ["1", "2", "Fizz"]
```

`pytest` → **FAIL**.

### Green:
```python
def fizz_buzz(n):
    wynik = []
    for i in range(1, n + 1):
        if i % 3 == 0:
            wynik.append("Fizz")
        else:
            wynik.append(str(i))
    return wynik
```

`pytest` → **PASS**.

### Red — Buzz:
```python
def test_piatka_to_buzz():
    assert fizz_buzz(5) == ["1", "2", "Fizz", "4", "Buzz"]
```

`pytest` → **FAIL**.

### Green:
```python
def fizz_buzz(n):
    wynik = []
    for i in range(1, n + 1):
        if i % 3 == 0:
            wynik.append("Fizz")
        elif i % 5 == 0:
            wynik.append("Buzz")
        else:
            wynik.append(str(i))
    return wynik
```

`pytest` → **PASS**.

### Red — FizzBuzz:
```python
def test_pietnastka_to_fizzbuzz():
    assert fizz_buzz(15)[-1] == "FizzBuzz"
```

`pytest` → **FAIL**.

### Green:
```python
def fizz_buzz(n):
    wynik = []
    for i in range(1, n + 1):
        if i % 15 == 0:
            wynik.append("FizzBuzz")
        elif i % 3 == 0:
            wynik.append("Fizz")
        elif i % 5 == 0:
            wynik.append("Buzz")
        else:
            wynik.append(str(i))
    return wynik
```

`pytest` → **PASS**. ✅

### Refactor:
- Można czyściej? Tak — np. zamienić if na słownik. Ale dla początkującego **nie pchaj się** za bardzo. "Działa, czytelne, testy zielone" → refactor opcjonalny.

**Pełna parametryzacja jako test końcowy:**
```python
@pytest.mark.parametrize("n, oczekiwane", [
    (3, ["1", "2", "Fizz"]),
    (5, ["1", "2", "Fizz", "4", "Buzz"]),
    (15, ["1","2","Fizz","4","Buzz","Fizz","7","8","Fizz","Buzz","11","Fizz","13","14","FizzBuzz"]),
])
def test_fizzbuzz(n, oczekiwane):
    assert fizz_buzz(n) == oczekiwane
```

## Krok 4 — Pogłębienie (10 min)

**Kiedy TDD ma sens:**
- Funkcje o **jasno określonej** specyfikacji (parsowanie, walidacja, kalkulacje)
- Bug-fixing — najpierw test odtwarzający bug, potem fix
- Kod biznesowy, który ma być **stabilny** i często modyfikowany

**Kiedy TDD utrudnia:**
- **Eksperymenty/prototypy** — nie wiesz jeszcze co chcesz
- **UI / wizualne efekty** — trudno opisać testem
- **Integracje z zewnętrznymi systemami** — wolniejsze, trzeba mockować

**Reguły TDD:**
- Pisz **minimalny** kod, żeby test przeszedł (nie "wszystko na zapas")
- Najpierw test — który **musi padać** (Red). Inaczej nie wiesz, czy test naprawdę coś sprawdza
- Refactor TYLKO przy zielonych testach

**Typowe błędy:**
- Pisanie kodu i testu **równocześnie** — pokusa wielka, ale tracisz dyscyplinę.
- Pisanie testu, który **przechodzi od razu** (bez Red) — może test nic nie sprawdza.
- Testy zbyt szczegółowe — łamią się przy każdym refactoringu, frustrują.

## Krok 5 — Ćwiczenie
→ Skill `cwiczenie`. Temat: "TDD". Sugerowane zadania:
- 🔥 Funkcja `najwiekszy(liczby)` (zwraca najwiekszą z listy). Najpierw test, potem implementacja.
- ⭐ Funkcja `palindrom(slowo)` (True jeśli czyta się tak samo w obu kierunkach). TDD pełnym cyklem: test dla "kajak", potem dla "abba", potem dla "Anna" (case-insensitive), potem dla "" (edge case).
- ⚡ Klasa `Stos` (LIFO) — metody `push`, `pop`, `peek`, `is_empty`. TDD: 1) pusty stos jest empty, 2) po push nie jest empty, 3) push i pop daje to samo, 4) pop z pustego rzuca wyjątek.

## Pułapki
- **Pominięcie Red** — bez "test musi padać najpierw" możesz mieć bezużyteczne testy.
- **Refactor bez zielonych testów** — psujesz, nie wiesz że psujesz, bo testy nie wpadły.
- **Nadmiar mockowania** — testy stają się "testami kodu testów", nie funkcji.
- **TDD na wszystko** — czasem szybciej napisać funkcję, potem 2 testy. Wybieraj sytuacje.

## Notatki tutora
- **FizzBuzz to klasyk** — niech uczeń przejdzie pełny cykl Red-Green-Refactor co najmniej raz. Inaczej TDD pozostaje teorią.
- **Nie ucz dogmatycznie** — TDD to **narzędzie**, nie religia. Czasem wystarczy "test po fakcie".
- Jeśli uczeń mówi "ale to dłużej" — odpowiedz: piszesz dłużej, debugujesz znacznie krócej. Bilans dodatni.
