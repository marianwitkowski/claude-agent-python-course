# Lekcja 6.3 — Debugger: śledzenie kodu krok po kroku

## Cel
Po lekcji uczeń:
- Wstawia **breakpoint** w VS Code (kliknięcie obok numeru linii)
- Uruchamia debugger (`F5`)
- Używa: Step Over (`F10`), Step Into (`F11`), Continue (`F5`)
- Ogląda zmienne w panelu Variables / hover
- Wie, kiedy debugger jest lepszy niż `print` (i kiedy `print` wystarczy)

## Krok 1 — Zakotwiczenie (3 min)
**Pytanie wejściowe:**
> "Czytasz książkę kucharską i przepis nie wychodzi. Co byś zrobił — zacząłbyś od początku patrząc tylko na efekt, czy zatrzymał się po każdym kroku, żeby sprawdzić co masz w garnku?"

**Co chcesz usłyszeć:** zatrzymać się po każdym kroku, zajrzeć do garnka. To dokładnie robi debugger — zatrzymuje program i pozwala obejrzeć "co jest w garnku" (zmienne) w danym momencie.

## Krok 2 — Mostek (5 min)
**Mostek:** "Debugger to narzędzie do **chodzenia po kodzie krok po kroku**. Możesz zatrzymać program w wybranym miejscu (**breakpoint**), zobaczyć wszystkie zmienne i wykonywać po jednej linii. To **mikroskop** do diagnostyki kodu."

**Bez kodu w mostku — zaraz wszystko zobaczy na żywo w VS Code.**

## Krok 3 — Eksperyment (15-20 min)

Stwórz plik `kurs/zadania/06-debug/test.py`:
```python
def srednia(liczby):
    suma = 0
    for liczba in liczby:
        suma += liczba
    return suma / len(liczby)

oceny = [4, 5, 3, 4, 5]
wynik = srednia(oceny)
print(f"Średnia: {wynik}")
```

**Krok po kroku w VS Code:**

1. **Wstaw breakpoint:** kliknij po lewej stronie numeru linii `suma = 0` (linia 2). Pojawi się czerwona kropka.

2. **Uruchom debugger:** menu Run → Start Debugging (`F5`). VS Code może zapytać o "Python File" — wybierz.

3. **Program zatrzymał się** przed linią 2. Pasek wykonania jest na linii 2.

4. **Panel Variables** (lewa strona) — zobacz: `liczby = [4, 5, 3, 4, 5]`, `suma` jeszcze nie ma.

5. **Step Over (`F10`)** — wykonaj bieżącą linię i przejdź do następnej. `suma` pojawia się jako `0`.

6. **`F10` jeszcze raz** — wchodzimy w pętlę, `liczba` to `4`.

7. **`F10`** — `suma` staje się `4`.

8. **Continue (`F5`)** — uruchom do następnego breakpointu lub końca.

**Hover nad zmienną:** w trakcie debuggowania najedź myszą na nazwę zmiennej w kodzie — pokaże aktualną wartość.

**Watch (zaawansowane):** prawy klik w panelu Variables → Add to Watch. Możesz śledzić **wyrażenie** (np. `len(liczby)`).

**Stack:** panel Call Stack pokazuje stos wywołań — w której funkcji jesteśmy.

## Krok 4 — Pogłębienie (10 min)

**Step Into vs Step Over:**
- **`F10` (Step Over)** — wykonuje funkcję jako "czarną skrzynkę". Skacze do następnej linii w bieżącej funkcji.
- **`F11` (Step Into)** — wchodzi do funkcji wywołanej w bieżącej linii. Możesz zobaczyć co się dzieje wewnątrz.
- **`Shift+F11` (Step Out)** — wyjdź z bieżącej funkcji, wróć do miejsca wywołania.

**Conditional breakpoint:** prawy klik na breakpoint → Edit Breakpoint → Expression. Np. `liczba > 4` — zatrzyma się **tylko** gdy warunek spełniony.

**Praktyczny scenariusz** — buggy program:
```python
def odejmij(a, b):
    return a + b   # CELOWY BŁĄD!

print(odejmij(10, 3))  # Spodziewamy 7, dostajemy 13
```
Niech uczeń **bez patrzenia w kod** użyje debugger, żeby zobaczyć "co tu jest źle". Step Into przy wywołaniu → widzi `a + b` zamiast `a - b`.

**Debugger vs `print`:**
| Sytuacja                       | Wybór    |
| ------------------------------ | -------- |
| Sprawdzenie 1-2 zmiennych      | `print`  |
| Skomplikowany przepływ         | debugger |
| Pętla z 1000 iteracji          | debugger (z conditional) |
| Krótki skrypt, szybka diagnoza | `print`  |
| Złapanie momentu błędu         | debugger (breakpoint + reproduce) |

## Krok 5 — Ćwiczenie
→ Skill `cwiczenie`. Temat: "debugger". Sugerowane zadania:
- 🔥 Stwórz funkcję z bugiem (np. `def kwadrat(x): return x * 2`). Użyj debuggera, znajdź błąd. Napraw.
- ⭐ Funkcja licząca silnię — z literówką w warunku pętli. Użyj debugger by zobaczyć, kiedy pętla się kończy.
- ⚡ Plik z 10 imionami. Funkcja `najdluzsze(imiona)` ma zwrócić najdłuższe. Użyj debugger by zobaczyć, jak działa porównywanie. (Bonus: użyj `max(imiona, key=len)` i porównaj rozwiązania.)

## Pułapki
- **Breakpoint nie ustawiony / VS Code nie zainstalowany Python extension** — debugger nie zadziała.
- **Nieznajomość różnicy Step Over vs Step Into** — wchodzisz w funkcje wbudowane (np. `print`), gubisz się.
- **Zapomniany breakpoint po debug** — debugger się zatrzymuje "z niewiadomego powodu" przy następnym uruchomieniu. Wyłącz wszystkie breakpointy (lub kliknij ponownie).
- **Dane z `input()` w debuggerze** — VS Code otwiera Debug Console; tam wpisz odpowiedzi.

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)
- **VS Code zamiast PyCharm** — repo poleca PyCharm Community. W VS Code z rozszerzeniem Python debugger jest równie potężny, prostszy w użyciu. To rekomendacja 2026.
- **AI-assisted debugging** (Claude Code, Copilot) — wzmianka: dziś AI też potrafi czytać traceback i sugerować poprawki. To uzupełnienie debuggera, nie zamiennik. Najpierw zrozum sam, potem ewentualnie spytaj AI.
- **`breakpoint()` w kodzie** (3.7+) — wstaw `breakpoint()` w pliku, uruchom **normalnie** (`python3 plik.py`), program zatrzyma się w terminalu w trybie `pdb`. Komendy: `n` (next), `s` (step), `c` (continue), `p zmienna` (print), `q` (quit). Wzmiankuj jako "bez IDE też się da".

## Notatki tutora
- **Debugger to umiejętność praktyczna** — bez 10 minut praktyki uczeń nie poczuje korzyści. Idź spokojnie, kliknij za nim pierwsze breakpointy.
- **Nie wprowadzaj `pdb` od razu** — interfejs tekstowy zniechęca początkujących. VS Code wystarczy.
- Pokaż, jak **rozwiązać konkretny bug** za pomocą debuggera — najlepiej historię z życia.
- Jeśli uczeń mówi "wolę printami" — pozwól. Powiedz: są zadania, w których debugger jest 10× szybszy, ale `print` to OK. Z czasem wybierze sam.
