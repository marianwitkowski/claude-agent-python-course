# Lekcja 11.3 — Testy, błędy, dokumentacja

## Cel
Po lekcji uczeń:
- Ma testy pokrywające **kluczowe ścieżki** projektu (>= 60% pokrycia)
- Obsługuje błędy w punktach kontaktu z użytkownikiem / siecią / plikami
- Pisze docstring w funkcjach publicznych
- Ma działający `README.md` z instrukcją instalacji i użycia

## Krok 1 — Zakotwiczenie (3 min)
**Pytanie wejściowe:**
> "Twój projekt działa idealnie u Ciebie. Wysyłasz znajomemu. On uruchamia — nie działa. Czemu?"

**Co chcesz usłyszeć:** brak instrukcji jak zainstalować, brak walidacji wejść (znajomy podał coś dziwnego), nie testowałeś edge cases. To jest **moduł 11.3**.

## Krok 2 — Mostek (5 min)
**Mostek:** "Projekt 'działa u mnie' to za mało. Trzeba:
1. **Testy** — masz pewność, że nie zepsujesz przy następnej zmianie
2. **Błędy** — program nie umiera od dziwnego wejścia
3. **Dokumentacja** — ktoś inny (lub TY za 6 miesięcy) wie jak uruchomić"

## Krok 3 — Eksperyment (20-30 min)

### A. Testy — pokrycie kluczowych ścieżek

Z MVP TODO-CLI z 11.2:

`tests/test_main.py`:
```python
import json
from pathlib import Path
import pytest
from src import main

@pytest.fixture
def tmp_todo(tmp_path, monkeypatch):
    plik = tmp_path / "todo.json"
    monkeypatch.setattr(main, "TODO_FILE", plik)
    return plik

def test_pusta_lista(tmp_todo):
    assert main.wczytaj() == []

def test_dodaj_pierwsze(tmp_todo):
    main.dodaj("kup mleko")
    dane = json.loads(tmp_todo.read_text(encoding="utf-8"))
    assert dane == [{"id": 1, "tekst": "kup mleko", "zrobione": False}]

def test_dodaj_drugie(tmp_todo):
    main.dodaj("a")
    main.dodaj("b")
    dane = main.wczytaj()
    assert len(dane) == 2
    assert dane[1]["id"] == 2

def test_dodaj_polskie_znaki(tmp_todo):
    main.dodaj("zażółć gęślą jaźń")
    dane = main.wczytaj()
    assert dane[0]["tekst"] == "zażółć gęślą jaźń"

@pytest.mark.parametrize("input_text, oczekiwane_id", [
    ("zad1", 1),
    ("zad2", 2),
    ("zad3", 3),
])
def test_kolejne_id(tmp_todo, input_text, oczekiwane_id):
    if oczekiwane_id > 1:
        for i in range(1, oczekiwane_id):
            main.dodaj(f"przedni {i}")
    main.dodaj(input_text)
    dane = main.wczytaj()
    assert dane[-1]["id"] == oczekiwane_id
```

Uruchom `pytest -v` — wszystkie powinny przejść.

**Coverage** (opcjonalnie):
```bash
pip install pytest-cov
pytest --cov=src
```

Cel: >= **60-70%** pokrycia (dla hobby projektu). >80% dla biznesowych. **100% to często overkill.**

### B. Obsługa błędów — punkty kontaktu

Identyfikujcie miejsca, w których program może paść:
1. **CLI argumenty** — brak komendy, zły format
2. **Plik JSON** — uszkodzony, brak uprawnień
3. **ID zadania** — nie istnieje, ujemny
4. **Polskie znaki / encoding** — Windows głównie

Dodaj obsługę:
```python
def wczytaj() -> list:
    if not TODO_FILE.exists():
        return []
    try:
        return json.loads(TODO_FILE.read_text(encoding="utf-8"))
    except json.JSONDecodeError:
        print(f"BŁĄD: plik {TODO_FILE} jest uszkodzony")
        sys.exit(1)
    except PermissionError:
        print(f"BŁĄD: brak uprawnień do {TODO_FILE}")
        sys.exit(1)

def usun(id: int) -> None:
    zadania = wczytaj()
    pasujace = [z for z in zadania if z["id"] == id]
    if not pasujace:
        print(f"BŁĄD: nie ma zadania o id {id}")
        sys.exit(1)
    zadania = [z for z in zadania if z["id"] != id]
    zapisz(zadania)
    print(f"Usunięto #{id}")
```

### C. Dokumentacja — docstring + README

**Docstring** — opis funkcji wewnątrz `"""..."""`:

```python
def dodaj(tekst: str) -> None:
    """Dodaje nowe zadanie do listy.

    Args:
        tekst: Treść zadania, niepusty string.

    Side effects:
        Zapisuje zmianę do pliku TODO_FILE.

    Examples:
        >>> dodaj("kup mleko")
        Dodano #1: kup mleko
    """
    ...
```

VS Code podpowie ten docstring, gdy najedziesz na wywołanie funkcji. **Pisz docstringi dla publicznych funkcji** — nie wszystkich.

**README.md** — szablon:

```markdown

## Krok 4 — Pogłębienie (10-15 min)

**Co testować, a czego nie:**

**TAK:**
- Funkcje z logiką (obliczenia, transformacje)
- Edge cases (pusty input, ujemne liczby, polskie znaki)
- Punkty kontaktu (zapis/odczyt pliku, parsowanie)

**NIE (lub mało):**
- Funkcje wbudowane (już są przetestowane)
- Trywialne settery/gettery
- Wizualne — wykresy, GUI

**Co obsługiwać try/except, a czego nie:**

**TAK:**
- I/O (sieć, dyski) — może paść
- Parsowanie zewnętrznych danych (JSON, CSV, input użytkownika)
- Wywołania zewnętrznych API

**NIE:**
- Każda linijka kodu — nie ma sensu
- Logika programu (jeśli funkcja przyjmuje int, nie sprawdzaj że to int — to obowiązek wołającego)

**Linter — `ruff`:**
```bash
pip install ruff
ruff check src/
ruff format src/
```
Wyłapuje nieużywane importy, błędy stylu, niespójności. Standardem 2026.

## Krok 5 — Ćwiczenie
→ To **rozszerzenie projektu**:
- 🔥 Dodaj co najmniej 5 testów `pytest`
- ⭐ Obsłuż 3 scenariusze błędów (brak pliku, zły JSON, niewłaściwe ID)
- ⚡ Napisz pełen `README.md` (instalacja, użycie, testy, limitacje)

## Pułapki
- **100% pokrycia testami** — nie zawsze celowe. Pokryj **kluczowe ścieżki**.
- **Testowanie implementacji zamiast zachowania** — testuj "co funkcja zwraca", nie "jakie ma zmienne wewnętrzne".
- **Brak dokumentacji** — projekt umiera za 3 miesiące, gdy nie pamiętasz jak go uruchomić.
- **Łapanie zbyt szerokich wyjątków** (`except Exception`) — ukrywa prawdziwe błędy.
- **Hardcoded ścieżki w testach** — używaj `tmp_path` fixture pytesta.

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)
- **`ruff` zamiast `pylint`/`flake8`/`black`** — wszystko w jednym, szybsze.
- **`mypy` lub `pyright`** — statyczne sprawdzanie typów. Wzmianka, dla zaawansowanych.
- **AI-generated docs** — Claude Code może wygenerować docstringi i README z kodu. Korzystaj, ale weryfikuj.

## Notatki tutora
- **Nie wymuszaj 100% coverage** — przegięcie. 60-70% wystarczy do nauki.
- **README jest często niedoceniane** — to **wizytówka** projektu. Niech uczeń poświęci 30 minut.
- **Testowanie po fakcie** może okazać się trudne — uczeń poczuje wagę TDD (lekcja 8.3).
