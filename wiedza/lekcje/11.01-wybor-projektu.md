# Lekcja 11.1 — Wybór projektu i specyfikacja

## Cel
Po lekcji uczeń:
- Wybiera **konkretny** projekt dopasowany do swojego celu (praca / dane / hobby / szkoła)
- Pisze **specyfikację** w `kurs/projekt/SPECYFIKACJA.md`: co robi, dla kogo, co NIE robi
- Dzieli projekt na 5-10 mniejszych zadań (TODO)
- Wie, że "ukończony projekt" > "ambitny niedokończony projekt"

## Krok 1 — Zakotwiczenie (5 min)
**Pytanie wejściowe:**
> "Mówisz znajomemu: 'Buduję dom'. Czy to wystarczająca informacja? Co byś musiał doprecyzować, żeby ktoś inny zrozumiał o co chodzi?"

**Co chcesz usłyszeć:** ile pokoi, jaki budżet, gdzie, dla kogo, kiedy. **Sprecyzowanie scope'u** to **najważniejszy etap** każdego projektu.

## Krok 2 — Mostek (5 min)
**Mostek:** "Programowanie też zaczynamy od specyfikacji. **Co dokładnie ma robić aplikacja?** **Co świadomie pomijamy?** Bez tego — projekt rośnie w nieskończoność i nigdy nie kończy się."

**Reguła #1 dla pierwszego projektu:** "**MVP** — Minimum Viable Product. Działa, ale tylko najbardziej podstawowa funkcjonalność. Reszta — w późniejszych iteracjach."

## Krok 3 — Eksperyment (20 min)

### Propozycje projektów wg celu ucznia:

**Cel: PRACA / AUTOMATYZACJA**
- **Skrypt zmieniający nazwy plików** — wczytaj katalog, zmień nazwy wg wzorca (np. dodaj datę, prefix). Idealne pierwsze "narzędzie".
- **Mini-CLI do TODO** — dodawanie, listowanie, oznaczanie zrobione, zapis do pliku JSON.
- **Logi → raport** — wczytaj plik logów, policz statystyki, wypisz raport.

**Cel: DANE / ANALIZA**
- **CSV explorer** — wczytaj plik CSV, wypisz statystyki kolumn, najczęstsze wartości.
- **Analizator notatek** — folder z plikami `.md`, policz słowa, ile plików, lista tagów.
- **Generator wykresów** — z danych CSV, użyj `matplotlib` (zewn., poza scope, ale wzmianka).

**Cel: HOBBY / GRY**
- **Wisielec (tekstowo)** — gra w terminalu, lista słów w pliku, podpowiadanie liter.
- **Quiz** — pytania w pliku JSON, losowanie, śledzenie wyniku.
- **RPG-text** — eksploracja, dialogi, walka z prostymi przeciwnikami.

**Cel: SZKOŁA / MATEMATYKA**
- **Kalkulator zadań tekstowych** — parsuje proste zdania ("Tata ma X jabłek...") i odpowiada.
- **Generator zadań matematycznych** — losuje zadania, sprawdza odpowiedzi, prowadzi statystykę.
- **Konwerter jednostek** — kg/funt, km/mile, etc.

### Wybór konkretnego projektu

Niech uczeń wybierze **jeden** projekt (lub zaproponuje własny). Następnie razem napisz specyfikację.

### Specyfikacja — szablon

Stwórz plik `kurs/projekt/SPECYFIKACJA.md`:

```markdown
# Mini-CLI TODO

## Co robi
Prosta aplikacja zarządzająca listą zadań z terminala.
Dane przechowuje w pliku `todo.json`.

## Funkcjonalności (MVP)
1. Dodaj zadanie: `python3 todo.py add "kup mleko"`
2. Lista wszystkich: `python3 todo.py list`
3. Oznacz jako zrobione: `python3 todo.py done 3` (po ID)
4. Usuń: `python3 todo.py remove 3`

## Co NIE robi (świadomie)
- Priorytety zadań
- Daty deadline
- Wiele list (kategorie)
- Interfejs graficzny

## Format danych w `todo.json`
\`\`\`json
[
  {"id": 1, "tekst": "kup mleko", "zrobione": false},
  {"id": 2, "tekst": "wynieść śmieci", "zrobione": true}
]
\`\`\`

## TODO — etapy
- [ ] Wczytywanie/zapisywanie JSON
- [ ] Komenda `add`
- [ ] Komenda `list` (z formatowaniem)
- [ ] Komenda `done`
- [ ] Komenda `remove`
- [ ] Obsługa argumentów CLI (`sys.argv`)
- [ ] Obsługa błędów (zły ID, pusty plik)
- [ ] Testy `pytest`
- [ ] README
```

## Krok 4 — Pogłębienie (10 min)

**Co charakteryzuje DOBRY pierwszy projekt:**
- Skończony w **8-15 godzinach** pracy
- Używa **min. 5 modułów** z kursu (typy, funkcje, pliki, struktury, błędy)
- Ma **wyraźny scope** — wiesz kiedy "skończone"
- Możesz pokazać innym (uruchamia się, robi coś widocznego)
- Nadaje się do **rozszerzenia** (jeśli chcesz iść dalej)

**Co charakteryzuje ZŁY pierwszy projekt:**
- "Klon Slacka" / "Aplikacja jak Spotify" — za duże
- Zależy od bibliotek, których nie umiesz (PyQt, Django bez wcześniejszej nauki)
- Brak konkretu — "narzędzie ML do analizy" (ale czego? po co?)
- Brak końca — wiecznie "jeszcze jedna feature"

**Stack projektu (rekomendacja 2026):**
- Python 3.12+
- `venv` (z lekcji 9.2) lub `uv`
- `pyproject.toml` z dependencies
- `pytest` do testów
- `pathlib`, `json` (stdlib)
- `requests` jeśli sieć
- Git + README (lekcja 11.4)

## Krok 5 — Ćwiczenie
→ To nie jest klasyczne ćwiczenie z `cwiczenie` — to **wybór projektu**. Wykonaj razem z uczniem:

1. **Wybór projektu** — uczeń mówi co chce robić
2. **Specyfikacja** — wspólnie wypełnijcie `kurs/projekt/SPECYFIKACJA.md`
3. **TODO list** — rozbijcie projekt na 7-12 kroków
4. **Pierwszy commit** (opcjonalnie, jeśli uczeń umie git):
```bash
mkdir -p kurs/projekt
cd kurs/projekt
git init
# napisz README.md i SPECYFIKACJA.md
git add .
git commit -m "Specyfikacja projektu"
```

## Pułapki
- **Za duży zakres** — najczęstszy błąd. Tnij. MVP najpierw.
- **Brak specyfikacji** — projekt rośnie w nieskończoność.
- **Wybór projektu opartego o niezbędne biblioteki, których nie znasz** — ekran graficzny, ML, web. Trzymaj się stdlib + ewent. `requests`.
- **Brak "co NIE robi"** — bez tego trudno powiedzieć "skończone".
- **Perfekcjonizm** — pierwszy projekt nie musi być piękny. Ma działać.

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)
- **AI-assisted coding** — Claude Code może przyspieszyć Twój projekt. Reguła: najpierw zrozum SAM, potem ewentualnie poproś AI o pomoc. Inaczej tracisz naukę.
- **Open source na końcu** — gdy projekt działa, opublikuj na GitHubie. Pierwszy publiczny projekt to ważny krok.

## Notatki tutora
- **Nie wymuszaj projektu z listy** — uczeń wie najlepiej co go inspiruje.
- **Specyfikacja w 30 minutach** — nie spędzaj 3 godzin na "doskonałym planie". Mniej > więcej.
- **TODO list to plan na **8-15 godzin** — jeśli wychodzi na 40h, **tnij**.
- **"Co NIE robi" jest kluczowe** — niech uczeń **świadomie** odrzuci funkcje.
