# Lekcja 8.1 — Wyjątki: `raise`, hierarchia, własne klasy

## Cel
Po lekcji uczeń:
- Sam **rzuca** wyjątek (`raise ValueError("opis")`)
- Wie kiedy rzucać (walidacja danych) a kiedy łapać (niepewne operacje)
- Tworzy własną klasę wyjątku przez dziedziczenie po `Exception`
- Czyta hierarchię: `Exception → ValueError`, `Exception → MyError`

## Krok 1 — Zakotwiczenie (5 min)
**Pytanie wejściowe:**
> "Kasjer w sklepie widzi, że dajesz mu 5 zł za zakupy za 50 zł. Co robi? Czy próbuje 'udać że jest OK'?"

**Co chcesz usłyszeć:** sygnalizuje problem ("brakuje 45 zł"), nie idzie dalej z transakcją. To `raise` — wczesne wykrycie i sygnalizacja problemu.

## Krok 2 — Mostek (5 min)
**Mostek:** "Lekcja 6.2 nauczyła Cię **łapać** wyjątki. Teraz nauczysz się je **rzucać** — sygnalizować, że coś jest nie tak. Funkcja z błędnymi danymi powinna natychmiast krzyknąć, a nie udawać że jest OK i pracować dalej."

**Minimalny przykład:**
```python
def pobierz_wiek(rok_urodzenia):
    if rok_urodzenia > 2026:
        raise ValueError(f"Rok urodzenia {rok_urodzenia} jest w przyszłości")
    return 2026 - rok_urodzenia

print(pobierz_wiek(1990))    # 36
print(pobierz_wiek(2050))    # ValueError!
```

**Pytania:**
- "Co robi `raise`?" (przerywa funkcję, sygnalizuje błąd)
- "Czemu `ValueError` a nie inny?" (to wbudowany typ — "wartość niepoprawna")

## Krok 3 — Eksperyment (15 min)

1. **Rzucanie wyjątku:**
```python
def dziel(a, b):
    if b == 0:
        raise ZeroDivisionError("nie dzielimy przez zero")
    return a / b

dziel(10, 2)    # OK
dziel(10, 0)    # ZeroDivisionError z TWOIM komunikatem
```

2. **Łapanie własnego raise:**
```python
try:
    pobierz_wiek(2050)
except ValueError as e:
    print(f"Złapane: {e}")
```
Zwróć uwagę na `as e` — łapiesz referencję do obiektu wyjątku.

3. **Re-raise (przekazanie wyżej):**
```python
def przetworz(rok):
    try:
        return pobierz_wiek(rok)
    except ValueError as e:
        print(f"Logowanie błędu: {e}")
        raise   # przekaż wyjątek dalej
```

4. **Własna klasa wyjątku:**
```python
class BrakSrodkowError(Exception):
    pass

class Konto:
    def __init__(self, saldo=0):
        self.saldo = saldo

    def wyplac(self, kwota):
        if kwota > self.saldo:
            raise BrakSrodkowError(f"Saldo: {self.saldo}, próba: {kwota}")
        self.saldo -= kwota

konto = Konto(50)
try:
    konto.wyplac(100)
except BrakSrodkowError as e:
    print(f"Błąd: {e}")
```

**Po każdym pytaj:** "Co `raise` zrobił z programem?"

## Krok 4 — Pogłębienie (15 min)

**Hierarchia wbudowanych wyjątków (najczęstsze):**
```
BaseException
 └── Exception
      ├── ArithmeticError
      │    └── ZeroDivisionError
      ├── LookupError
      │    ├── IndexError
      │    └── KeyError
      ├── OSError
      │    └── FileNotFoundError
      ├── ValueError
      ├── TypeError
      └── RuntimeError
```

Wytłumacz: gdy łapiesz `Exception`, łapiesz **wszystko poniżej**. Gdy łapiesz `ValueError`, łapiesz tylko tę gałąź.

```python
try:
    int("abc")        # ValueError
except Exception:      # łapie też ValueError
    print("złapane")

try:
    int("abc")
except ZeroDivisionError:  # NIE łapie ValueError!
    print("nie złapane")
```

**Własne wyjątki — hierarchia:**
```python
class BladSklepu(Exception):
    pass

class BrakProduktuError(BladSklepu):
    pass

class BrakSrodkowError(BladSklepu):
    pass

try:
    raise BrakProduktuError("nie ma w magazynie")
except BladSklepu as e:    # łapie wszystkie z hierarchii sklepu
    print(f"Sklep: {e}")
```
Korzyść: możesz łapać "wszystkie błędy sklepu" jednym `except`.

**Łańcuch wyjątków (`raise ... from ...`):**
```python
try:
    int("abc")
except ValueError as e:
    raise RuntimeError("Coś poszło nie tak w parsowaniu") from e
```
Traceback pokaże oba — twój `RuntimeError` **i** oryginalny `ValueError`.

**Typowe błędy do sprowokowania:**
- `raise "tekst"` — nie działa, musi być **obiekt klasy wyjątku**: `raise ValueError("tekst")`.
- `class MyError:` (bez dziedziczenia po Exception) — `TypeError: exceptions must derive from BaseException`.
- Łapanie zbyt szerokiego wyjątku (`except Exception`) — może ukryć błędy programisty.

## Krok 5 — Ćwiczenie
→ Skill `cwiczenie`. Temat: "wyjątki". Sugerowane zadania:
- 🔥 Funkcja `wiek_z_roku(rok)` — rzuca `ValueError` dla roku w przyszłości lub <1900.
- ⭐ Klasa `Termometr` z `temperatura`. Metoda `ustaw(t)` rzuca `ValueError` jeśli `t < -50` lub `t > 100`.
- ⚡ Własny `MailValidationError(Exception)`. Funkcja `wyslij(email, tresc)` — rzuca `MailValidationError` jeśli email nie zawiera `@`. Złap i wypisz "logowanie problemu".

## Pułapki
- **`raise` bez argumentu** wewnątrz `except` — re-raise tego co złapałeś.
- **Łapanie zbyt szerokiego** (`except Exception` lub `except:`) — anty-idiom.
- **`raise` z literałem** (`raise "tekst"`) — TypeError. Trzeba klasy.
- **Klasa wyjątku bez dziedziczenia po Exception** — TypeError.
- **Cichy `pass` w `except`** — najgorszy nawyk. Zawsze logujemy / informujemy.
- **Łapanie `KeyboardInterrupt`** (`except:`) — uniemożliwiasz `Ctrl+C`. Bardzo zła praktyka.

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)
- **Lepsze tracebacki (3.11+, 3.13)** — z `^^^^^` pod miejscem błędu, kolorowanie.
- **Sugestie błędów (3.12+)** — `NameError: name 'lne' is not defined. Did you mean: 'len'?`
- **`ExceptionGroup` i `except*`** (3.11+):
```python
raise ExceptionGroup("wiele rzeczy", [ValueError("x"), TypeError("y")])

try:
    ...
except* ValueError as eg:
    ...
```
Wzmianka — dla zaawansowanych (async, paralelizm).
- **`except ValueError, TypeError:`** bez nawiasów (3.14, PEP 758) — wzmianka, nie używaj jeszcze.

## Notatki tutora
- **`raise` jest tak samo ważne jak `try`** — wielu początkujących tylko łapie. Pokaż "fail fast" — lepiej krzyczeć od razu.
- **Własne wyjątki** — pokaż, że to **3 linijki kodu**, a daje świetną organizację błędów w projekcie.
- **Nie wprowadzaj `__cause__`, `__context__`** — to detale.
