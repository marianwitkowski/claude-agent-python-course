# Lekcja 11.4 — Git, README, deploy

## Cel
Po lekcji uczeń:
- Inicjalizuje repo: `git init`, robi pierwszy commit
- Tworzy konto na GitHubie i pushuje projekt
- Pisze profesjonalny `README.md` z badge'ami
- Zna podstawy `.gitignore`
- (Opcjonalnie) wie jak udostępnić projekt jako pakiet

## Krok 1 — Zakotwiczenie (3 min)
**Pytanie wejściowe:**
> "Piszesz długi tekst. Co się dzieje, gdy zepsujesz coś nieodwracalnie? Jak chcesz móc cofnąć do wcześniejszej wersji?"

**Co chcesz usłyszeć:** historia zmian, możliwość cofnięcia. To **system kontroli wersji** — Git. Bez niego programowanie w XXI wieku jest niewyobrażalne.

## Krok 2 — Mostek (5 min)
**Mostek:** "**Git** to system, który zapisuje **snapshoty** twojego kodu w czasie. Możesz wrócić do każdej wersji, porównać zmiany, współpracować z innymi. **GitHub** to popularny hosting takich repozytoriów online."

W 2026 **Git to nie 'opcja' — to standard**. Każdy projekt programistyczny ma git.

## Krok 3 — Eksperyment (25-35 min)

### A. Inicjalizacja repo

```bash
cd kurs/projekt
git init
git status   # zobaczy untracked files
```

### B. `.gitignore` — co NIE commitować

`.gitignore`:
```
# Python
__pycache__/
*.pyc
.venv/
.pytest_cache/
*.egg-info/

# IDE
.vscode/
.idea/

# OS
.DS_Store

# Dane lokalne
todo.json
*.log
.env
```

**Reguła:** nie commituj:
- `.venv/` — odtwarzalne z `requirements.txt`
- Cache plików (`__pycache__/`)
- Tajemnice (`.env`, klucze API)
- Pliki edytora (`.vscode/settings.json` — czasem tak, czasem nie)
- Duże dane (`*.csv` jeśli wielkie)

### C. Pierwszy commit

```bash
git status              # co jest do commita
git add .               # dodaj wszystko (z wyjątkiem .gitignore)
git status              # teraz "staged"
git commit -m "Pierwszy commit: MVP TODO-CLI"
git log                 # historia
```

### D. Konfiguracja git (raz, na zawsze)

```bash
git config --global user.name "Twoje Imię"
git config --global user.email "twoj@email.com"
```

### E. Konto GitHub + push

1. Zarejestruj się na https://github.com (jeśli jeszcze nie)
2. Stwórz **nowe repozytorium** w GitHub (przez UI): nazwa "moj-projekt", **bez README** (już masz lokalnie)
3. Połącz z lokalnym repo:
```bash
git remote add origin https://github.com/USERNAME/moj-projekt.git
git branch -M main
git push -u origin main
```
4. Odśwież stronę GitHub — twój projekt jest online.

### F. Workflow dnia codziennego

```bash
# Po zmianach:
git status              # co się zmieniło
git diff                # konkretne zmiany
git add <plik>          # lub git add . (wszystko)
git commit -m "feature: dodano komendę done"
git push                # wyślij na GitHub
```

### G. Praca z `branchami` (wzmianka):

```bash
git branch feature/usun-zadanie   # nowy branch
git checkout feature/usun-zadanie # przełącz
# ...prace...
git add . && git commit -m "feature: usuwanie"
git push -u origin feature/usun-zadanie

# Potem na GitHub: utwórz Pull Request → review → merge
```
Dla solo projektu nie musisz, ale dla zespołowego — standard.

**Po każdym kroku pytaj:** "Co Git zrobił? Co `git status` pokazuje teraz?"

## Krok 4 — Pogłębienie (15 min)

### A. README z badge'ami (opcjonalnie)

```markdown
# Mini-CLI TODO

![Python](https://img.shields.io/badge/python-3.12+-blue)
![Tests](https://github.com/USER/REPO/actions/workflows/test.yml/badge.svg)
![License](https://img.shields.io/badge/license-MIT-green)

Krótki opis projektu...
```

### B. LICENSE — wybierz licencję

Polecaj **MIT** (najprostsza, permissive):
```
MIT License

Copyright (c) 2026 Twoje Imię

Permission is hereby granted, free of charge, to any person...
```
Pełen tekst: https://opensource.org/licenses/MIT

### C. Continuous Integration (zaawansowane)

GitHub Actions — `.github/workflows/test.yml`:
```yaml
name: tests

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install -e ".[dev]"
      - run: pytest
```

Po pushu — GitHub uruchomi testy. Wzmianka.

### D. Publikacja jako pakiet (zaawansowane)

Jeśli twój projekt jest narzędziem, możesz opublikować w PyPI:
```bash
pip install build twine
python -m build
twine upload dist/*
```
Wymaga konta PyPI. Dla pierwszego projektu — **pomiń**.

### E. Typowe błędy

- **Commit całego `.venv/`** — 100MB+ trash w repo. Zawsze `.gitignore`.
- **Commit kluczy API / haseł** — security risk. Używaj `.env` (w `.gitignore`).
- **Wielki commit** ("zmieniłem wszystko") — trudno zrozumieć. Drobne commity są lepsze.
- **Commit "WIP"** — OK lokalnie, ale przed pushem squashuj.
- **`git push --force` na main** — może wymazać pracę innych. Nigdy.

## Krok 5 — Ćwiczenie
→ Końcowe ćwiczenie z PROJEKTU:
- 🔥 `git init`, dodaj `.gitignore`, zrób 3 commity z różnymi zmianami
- ⭐ Konto GitHub + repo + push. Daj agentowi link, niech sprawdzi że widoczne publicznie.
- ⚡ Dodaj LICENSE (MIT), badge w README, `pyproject.toml` z metadanymi. Bonus: CI z GitHub Actions.

## Pułapki
- **Commit `.env` lub kluczy** — security risk. Sprawdź **zanim** zrobisz `git push`.
- **Wielkie commity** — gdy pojawi się bug, trudno go znaleźć.
- **`git pull` zamiast `git fetch + merge`** — pull może zaskoczyć (auto-merge). Dla solo to OK.
- **Brak branch'y** dla feature'ów — w solo OK, w zespole konieczne.
- **`git push --force`** — niszczy historię innych.

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)
- **GitHub Actions** to standard CI. Łatwy do skonfigurowania.
- **`gh` CLI** (GitHub CLI) — tworzenie PR, issue z terminala. `brew install gh`.
- **Conventional Commits** — `feat:`, `fix:`, `docs:` w prefiksach. Wzmianka.
- **AI w git** — Copilot/Claude potrafią wygenerować dobry commit message ze zmian.

## Notatki tutora
- **Pierwszy push do GitHuba to PRZEŁOMOWY moment** — uczeń ma **publiczny projekt**. Sukces!
- **Nie wprowadzaj rebase, cherry-pick, reset** — to zaawansowane.
- **Daj uczniowi czas** na zrozumienie "po co commitować małe" — to wymaga praktyki.
- **Sugeruj `gh repo create`** jeśli `gh` zainstalowane — szybsze niż przez UI.
